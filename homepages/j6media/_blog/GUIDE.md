# 제이식스미디어 블로그 작업 설명서

제이식스미디어 홈페이지(www.j6media.co.kr)의 **행사 준비 블로그**(`/blog/`)에 지역별 정보 글을 올릴 때 따르는 규칙이다. 바로기획 `_blog/GUIDE.md`(HD기획 · 큰길이벤트기획 규칙을 옮긴 것)를 음향 · 조명 회사인 제이식스미디어에 맞게 옮겼다. 사람이 고칠 때도 이 문서를 먼저 고친다.

- 읽는 사람: 행사 음향 · 조명을 맡은 담당자 — 교회 예배 · 수련회 · 세미나 담당 목회자와 간사, 기업 행사 · 고객초청 음악회 담당자, 지자체 · 재단의 공식 행사 담당 주무관, 학교 축제 · 체육대회를 맡은 선생님, 전시 · 공연 기획자, 교회 · 카페 · 강당에 음향 · 영상 설비를 새로 들이려는 분.
- 목표: 네이버 웹문서 · 구글 · AI 검색(SEO · GEO · AEO)에서 "지역 + 행사 음향 · 조명 준비" 검색에 걸리는 것. 광고 글이 아니라 **담당자가 저장해 두고 싶은 체크리스트**여야 한다.
- 원칙: 틀린 정보 한 줄이 글 한 편보다 해롭다. **확인 못 한 것은 쓰지 않는다.** 그럴듯하게 지어낸 지역 이야기와 회사 약속이 가장 위험하다.
- 대표 네이버 블로그(blog.naver.com/martin301)는 대표가 직접 쓰는 별개의 블로그다. 이 `/blog/` 는 홈페이지 안의 정보 글 모음이고, 네이버 글을 베끼거나 글 안에서 언급하지 않는다(검사기가 막는다).

## 1. 순서

1. `node scripts/blog-plan.mjs` 로 다음에 쓸 글(지역 · 주제 · 키워드)을 받는다. 근거가 없는 조합(예: 현장기록 없는 지역에 그 지역 행사 경험처럼 보이는 주제)은 건너뛰고 다음 후보를 쓴다.
2. 글마다:
   1. `_blog/regions.json` 에서 그 지역의 `이동 · 동네 · 많은행사 · 주의 · 현장기록` 을 읽는다. **지역 이야기는 여기 있는 것과 출처를 단 사실만 쓴다.**
   2. 같은 주제로 다른 지역에 쓴 글이 있으면 읽되 **베끼지 않는다**. 목차부터 새로 짠다.
   3. 법 · 기준 · 기관 이야기는 `_blog/sources.json` 에 있는 출처와 그 `사실` 범위 안에서만 쓴다. 그 기관 도메인의 다른 주소는 검사기가 막는다. 필요한 기준이 없으면 그 내용은 쓰지 않는다(전기 용량 수치 · 무선마이크 주파수 규정 등은 아직 확인한 출처가 없다).
   4. 사진 3~4장을 `_blog/photos.json` 에서 고른다(5장).
   5. `_blog/posts/<날짜>-<slug>.json` 을 쓴다(3장). **`근거` 칸을 반드시 채운다.**
   6. `node scripts/blog-check.mjs --new <파일>` 이 통과할 때까지 고친다. 검사기를 통과시키려고 동네 이름이나 자료 문장을 억지로 끼워 넣지 않는다 — 그럴 거면 그 글을 버린다.
3. `node scripts/build-blog.mjs` 로 `/blog/` 를 다시 만든다(sitemap.xml · llms.txt · rss.xml 도 같이 갱신된다). 결과 HTML 은 손으로 고치지 않는다.
   - 블로그 페이지의 머리글 · 휴대폰 메뉴 · 바닥글은 `notice.html` 에서 빌려 온다(`tools/make_pages.py` 와 같은 방식). 메뉴를 바꾸면 notice.html 을 고치고 `python tools/make_pages.py` → `node scripts/build-blog.mjs` 순서로 다시 돌린다.
   - `python tools/make_pages.py` 는 sitemap.xml 을 통째로 다시 쓰므로(블로그 주소가 빠진다) 돌린 뒤에는 반드시 `node scripts/build-blog.mjs` 를 다시 돌린다.
   - `assets/style.css` 를 고치면 모든 html 의 `style.css?v=` 숫자를 하나 올린다(블로그는 notice.html 의 숫자를 그대로 따라간다).
4. 커밋 · 푸시. GitHub Pages 가 1분 안에 반영한다. 네이버 서치어드바이저 · IndexNow 알림은 검색 등록(소유 확인)을 마친 뒤 사람이 한다.

## 2. 절대 쓰지 않는 것

검사기(`scripts/blog-check.mjs`)가 일부를 막지만 전부는 못 막는다.

**① 회사가 하겠다고 한 적 없는 약속 · 서비스**
- 회사가 할 수 있다고 말하는 것은 4장 목록뿐이다. 그 밖의 것(천막 · 텐트, 무대 제작 · 트러스, 발전기, 의자 · 테이블, 현수막 · 포토존, MC · 사회자 · 공연팀 섭외, 레크리에이션, 케이터링 · 도시락, 에어바운스 등)은 빌려준다거나 해 준다고 쓰지 않는다. "담당자(주최 측)가 따로 확인할 일"로 쓴다.
- regions.json `주의` 칸의 작성자용 메모(「(작성자용)」으로 시작)를 글에 옮기지 않는다.
- 사이트에 없는 약속을 만들지 않는다 — "답사 무료", "당일 견적", "24시간 대기", "교회음향 지원사업 신청 받습니다" 같은 말은 제이식스미디어 사이트에 없다.

**② 회사 경험을 늘려 말하기**
- "수많은 행사를 맡아 왔습니다", "대형 축제도 대응해 왔습니다" 같은 말을 쓰지 않는다. 현장기록에 적힌 **행사 이름**으로만 말한다.
- 사이트 대문 · 회사소개의 설립 · 경력 표현(「2005년부터 2026년까지 계속 이어온 음향의 길」 · 「since 2005」 · 「2001」 · 대표 연혁), 「설치 15곳」 같은 현장 수, 「수백 명이 모이는 수련회」 같은 규모, 하나복 「10년이 넘었다」는 블로그에 쓰지 않는다(검사기가 막는다).

**③ 근거 없는 지역 이야기**
- 동네 이름에 특징을 붙이기("곤지암처럼 산 가까운 곳") — 동네 이름은 "(별내 · 순화궁로 등)"처럼 **괄호 속 나열로만** 쓴다. 괄호 바로 뒤에 "같은 · 처럼"을 붙이지 않는다.
- 문의 통계 지어내기("서울은 교회 음향 문의가 많습니다"), 지역 성격 지어내기, 다른 지역과 견주기.
- 대신 "체육관은 소리가 울리기 쉬운 공간입니다"처럼 **지역 이름을 붙이지 않은 일반 요령**으로 쓴다.
- 남양주 · 구리는 현장기록이 없다(지역 페이지에 「아직 정리된 기록이 없다」). 그 지역 행사 경험처럼 쓰지 않는다. 다른 지역 현장 이야기를 쓸 때는 그 현장의 지역 이름을 그대로 쓴다(예: "원주 오크밸리리조트 그랜드볼룸 수련회에서는 …").

**④ 그 밖에**
- 가격 · 단가 · "○○원" · 무료 · 비용 비율 — 견적은 행사 규모 · 장소 · 일정에 따라 달라 상담으로 안내한다.
- 회사 연혁 · 경력 연수 · 행사 건수 · 순위 · 만족도 · 후기 · 고객 발언.
- 행사 숫자(방문객 수 · 참석자 수). 「꿈의 해석」 스피커 27대 같은 **장비 구성 숫자**는 행사 이야기에 적힌 그대로라면 쓸 수 있다.
- 사진 장소 바꾸기 — 지역을 모르는 사진은 캡션에 지역을 쓰지 않는다. 사람 얼굴이 크게 나온 사진, 목록에 없는 사진, AI 그림.
- 다른 업체 비방, 다른 회사 이름(함께 일한 회사 포함). "무조건 · 100% · 보장".

## 3. 글 형식 (JSON)

| 칸 | 규칙 |
|---|---|
| `slug` | 한글 · 영소문자 · 숫자와 `-`, 70자 이하. 지역 이름 + 핵심 키워드 + 약속 |
| `date` | `YYYY-MM-DD`. 파일 이름은 `<date>-<slug>.json` |
| `region` | `_blog/regions.json` 의 slug (`namyangju`, `seoul` …) 또는 `common` |
| `topic` | `_blog/keywords.json` 의 topic. 같은 지역에 같은 topic 은 한 번만 |
| `title` | 15~50자. 지역 이름을 앞쪽에, 핵심 키워드를 통째로 |
| `description` | 70~160자. 누구에게 무엇을 정리했는지. 핵심 키워드 포함 |
| `keyword` | `{ "main": 핵심 키워드, "sub": [보조 키워드들] }` |
| `lead` | 80~420자. 첫 문장에 핵심 키워드와 결론 |
| `points` | 3~5개. 본문을 안 읽어도 답이 되는 문장 (AI 검색이 그대로 인용하는 자리) |
| `cover` | `{ "path", "alt", "caption" }` — 가로 사진만 |
| `sections` | 4~8개. `{ "h2": "1. …", "blocks": [ … ] }` — h2 하나 이상에 지역 이름이나 키워드 |
| `faq` | 2~6개. `{ "q", "a" }` — 실제로 받을 법한 질문. 답에서 새 약속을 만들지 않는다 |
| `근거` | **3개 이상.** `{ "내용": 본문에 그대로 있는 구절, "출처": "regions.json" 또는 이 글 sources 의 주소 }`. regions.json 근거는 25자 이하 핵심어로, 그중 하나 이상은 `이동 · 주의 · 현장기록`에서 |
| `sources` | `{ "name", "url" }` — 법 · 기준 · 기관을 말했으면 반드시. 공식 기관은 sources.json 주소 그대로 |

`blocks`: `{ "p" }` · `{ "ul": [] }` · `{ "ol": [] }` · `{ "table": { "head": [], "rows": [[]] } }` · `{ "img": { "path", "alt", "caption" } }` · `{ "tip": 현장 메모 }`
꾸밈은 `**굵게**` 와 `[글자](/주소 또는 https://…)` 뿐. 내부 주소는 `/quote.html` 처럼 `/` 로 시작해 쓴다(빌드가 페이지 깊이에 맞춰 `../` 로 바꾼다).

## 5. 사진

- `_blog/photos.json` 에 있고 `제외`가 없는 사진만. 표지 1장 + 본문 2~3장. **같은 묶음(같은 path 목록)에서 두 장을 쓰지 않는다.** 표지는 `방향`이 가로인 사진(검사기가 세로 표지를 막는다).
- path 는 `/assets/img/works/w<번호>.webp`(목록 카드는 빌드가 같은 번호의 `t<번호>.webp` 로 바꿔 쓴다).
- `alt` — 사진에 보이는 것(8~120자). `caption` — "장면 — 무엇을 보여 주는지". 목록의 `지역`이 비어 있으면 캡션에 지역을 쓰지 않는다. 지역이 있는 사진은 다른 지역 글에 써도 되지만 캡션의 지역은 사진의 지역 그대로.
- 일부 사진에는 대표 네이버 블로그 주소 워터마크가 찍혀 있다(그대로 써도 된다. 글에서 블로그를 언급하지는 않는다).
- 표지는 되도록 기존 글과 겹치지 않게.

## 6. 좋은 글의 기준

- 합니다체, 짧은 문장, 쉬운 말. 첫 문단이 답이다.
- 지역 사실 3가지 이상, 전부 근거가 있어야 한다(regions.json 의 이동 · 주의 · 현장기록이 가장 좋다. 동네 · 많은행사는 이름 나열로만).
- 표 1개 이상(체크리스트 · 준비표 · 견적 항목표). 내부 링크 2개 이상: `/quote.html` 반드시, 지역 페이지(`/areas/<slug>.html`), 관련 글(`/blog/<slug>/`).
- 견적 항목표(소제목에 「견적」)의 첫 칸은 자동 견적서 품목 이름으로만.
- 핵심 키워드는 제목 · 설명 · 첫 문단 · 소제목 하나에 자연스럽게(본문 12번 넘으면 경고).
- 본문 1800자 이상(2500자 권장). 같은 주제를 다른 지역에 쓸 때 본문이 30% 넘게 겹치면 막힌다.
